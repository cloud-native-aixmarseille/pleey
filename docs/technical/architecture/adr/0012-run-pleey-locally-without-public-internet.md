# ADR 0012: Run Pleey Locally Without Public Internet Access

- Status: Proposed
- Proposed date: 2026-10-09
- Accepted date: N/A

## Context

Issue [#508](https://github.com/cloud-native-aixmarseille/pleey/issues/508) asks that Pleey be able to run locally without an internet connection, as a prerequisite for the work in issue [#507](https://github.com/cloud-native-aixmarseille/pleey/issues/507). The repository already provides a Docker Compose development stack, but it does not define what “local” and “offline” guarantee, and the current bootstrap and runtime have different connectivity needs.

The current runtime uses local PostgreSQL, Valkey, Mailpit, and OpenTelemetry services. CAPTCHA challenges are generated by the backend, and the browser widget uses local WASM assets and the local API. However, the frontend imports Google Fonts at runtime. In addition, image builds use OS and npm package repositories, the setup path can pull Traefik, and development containers run `npm install` on startup. Therefore a running, pre-provisioned stack is closer to offline-capable than a cold setup, but neither the full runtime nor a first-time disconnected installation has a documented guarantee. See the [offline runtime audit](../../development/local-mode-audit.md) for evidence and a prioritized remediation plan.

This record sets a direction for future work; it does not assert that offline setup or runtime support is already implemented.

## Decision Drivers

- Core application journeys should not require a public service at runtime.
- The frontend should not make automatic third-party requests during ordinary use.
- A disconnected installation needs a repeatable, explicit artifact-preparation process.
- Local authentication protection and development recovery-mail flows must remain usable.
- Public-internet access should not be silently required by container startup or restart.
- Optional external navigation should remain distinguishable from a runtime dependency.
- The local development workflow should remain simple when internet access is available.

## Considered Options

### Option 1: Keep the current local stack and document its limitations

Continue using the existing Compose services and accept the external font request, online image/package acquisition, and install-on-start behavior. Document that connectivity or populated local caches are required.

### Option 2: Require all setup and runtime services to be reachable online

Use online third-party services for assets, challenge verification, email, or other integrations. This can simplify some local service configuration but makes local operation dependent on public availability and connectivity.

### Option 3: Define an offline-capable local mode with explicit artifact preparation

Keep the functional runtime self-hosted, eliminate default public runtime requests, and provide a documented process to prepare or transfer all required images and dependencies before disconnecting. Start and restart the application using only those local artifacts.

## Decision

Choose option 3 as the target for Pleey's supported local mode.

“Offline-capable” means that, after a documented preparation step has supplied the source and all required runtime/build artifacts to the machine, the application can start, restart, and support its core journeys without public-internet access. It does not promise that a new machine with only a source checkout can obtain source, Docker images, operating-system packages, or npm packages while disconnected. Artifact acquisition and local operation must be separate, explicit steps.

The following invariants apply to local-mode implementation:

1. Default browser and backend runtime behavior uses the local application or local services. No public third-party request may be required for core journeys.
2. Static assets, including CAPTCHA WASM and any fonts selected for the UI, are supplied locally. CAPTCHA challenge generation and verification remain local.
3. Compose-provided persistence, cache, development email, and telemetry stay inside the local environment. Any additional local service must be included in its topology and artifact requirements.
4. Image/dependency preparation is explicit and repeatable. Startup and restart do not run package installation or attempt to pull missing images.
5. Optional external links, such as configured feedback destinations, may be unavailable while offline and must not prevent application use.
6. Automated verification blocks public egress and checks browser requests and container startup, so later changes cannot silently weaken the offline guarantee.
7. The existing convenient online development setup may remain, but it must use the same local runtime boundaries and make its artifact-acquisition behavior clear.

## Consequences

### Positive

- The app's offline runtime contract is testable and clear to developers.
- Local development does not expose user journeys to third-party uptime or connectivity.
- Package/image acquisition is separated from application execution and can be prepared for air-gapped environments.
- Existing local CAPTCHA, database, cache, and mail services are retained rather than replaced with hosted dependencies.

### Negative

- Supporting disconnected first startup requires an artifact bundle or an equivalent preloading workflow and additional documentation.
- Removing startup-time package installation changes the convenience behavior of development containers; dependency changes will require an explicit install/build step.
- Locally bundling fonts or adding services introduces artifact licensing, size, maintenance, and update considerations.
- Offline smoke tests must distinguish legitimate local-network traffic from public egress and may require Docker-capable CI runners.

### Follow-Up

- Implement the findings and acceptance criteria in the [offline runtime audit and remediation plan](../../development/local-mode-audit.md).
- Remove the Google Fonts runtime import and verify all core browser journeys against a public-origin request allowlist.
- Define an artifact preparation/import workflow and make app startup independent of registries and package managers.
- Resolve the missing local Jaeger target or remove it from the local collector configuration.
- Add an egress-blocked startup, restart, and user-journey check before treating this ADR as accepted.
